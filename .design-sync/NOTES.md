**Bundler workarounds - all config-level, nothing under `src/` touched, nothing in `.ds-sync/lib/` forked:**

1. **Bare directory imports (`@/components/ui`, `@/lib/db`, `@/lib/contest`, `@/lib/themes`, `@/components/station-ui`, `@/components/map/hamclock/wall/controls`, + ~40 more barrel dirs).** `lib/bundle.mjs`'s `tsconfigPathsPlugin` resolves the `@/*` wildcard by trying extensions in order `['', '.ts', '.tsx', ..., '/index.ts', ...]` - since `''` is tried first and `existsSync()` doesn't distinguish files from directories, a bare `@/components/ui` import resolves to the *directory itself* before ever trying `/index.ts`, and esbuild fails with `Cannot read file "...": is a directory`. Fixed by writing a repo-specific tsconfig, `.design-sync/tsconfig.ds-sync.json` (generated once by scanning `find src -name index.ts -o -name index.tsx`), that lists an **exact** `paths` entry for every `src/**/index.ts(x)` directory pointing directly at its index file, inserted *before* the generic `@/*` wildcard entry (object key order = rule try order in the plugin). `config.json`'s `tsconfig` field points at this file instead of the repo's real `./tsconfig.json`. If a NEW barrel directory is added under `src/` later, re-run the same `find` + regenerate this file (see the node one-liner in build history / just re-derive it) or the same class of error will resurface for it.
2. **`virtual:pwa-register/react`** (imported by `ui/PWAUpdatePrompt.tsx`) is a Vite-plugin-pwa virtual module that only exists inside a real Vite build; esbuild can't resolve it. Same `tsconfig.ds-sync.json` `paths` mechanism redirects that bare specifier to `.design-sync/shims/virtual-pwa-register-react.ts`, a tiny local shim whose `useRegisterSW()` always returns `needRefresh: [false, setState]` (matches the hook's real "nothing pending" default) so `PWAUpdatePrompt` renders its natural empty state instead of crashing.
3. **`SpotRow` (`dx/DXSpotList/SpotRow.tsx`) pulled in `@react-three/fiber` + `@react-three/drei` + `react-reconciler`, which crashed the ENTIRE bundle on load** (`[SCHEDULER_MISSING]`, and every one of the 132 components failed `[BUNDLE_EXPORT]` in the same run - not just SpotRow's own card - because `@react-three/fiber` eagerly constructs its reconciler at module top-level, and SpotRow statically imports two tiny pure formatters, `getSpotAgeInfo`/`formatSpotAge`, from `map/LiveSpotArcs.tsx`, a full Three.js globe-overlay component esbuild can't tree-shake around due to top-level side effects). Fixed the same way: `tsconfig.ds-sync.json` redirects the bare specifier `@/components/map/LiveSpotArcs` to `.design-sync/shims/live-spot-arcs-age.ts`, a verbatim port of just those two pure Date-math functions (no React/Three deps). **Re-sync risk**: if `LiveSpotArcs.tsx`'s age-bucket thresholds/format ever change, this shim goes stale silently - diff it against the real file on future re-syncs of `SpotRow`.
4. **`cssEntry` local `@import` resolves relative to `ds-bundle/` (`OUT`), not relative to the importing file.** `package-build.mjs` appends `cfg.cssEntry`'s RAW file text verbatim into `_ds_bundle.css` (no `@import` resolution of its own); `package-validate.mjs`'s `[CSS_IMPORT_MISSING]` check then does `existsSync(join(OUT, importPath))`. `.design-sync/ds.css` (cssEntry) therefore imports the compiled app stylesheet as `@import "../.design-sync/.cache/app.css";` (one level up from `ds-bundle/`, not `./.cache/app.css` as the naive recipe would suggest) so it resolves correctly against `OUT`. **Re-sync risk / upload blocker**: this reaches *outside* `ds-bundle/` via `../`, which is fine for local `build`+`validate` but WILL dangle if `ds-bundle/` is ever uploaded/copied standalone (claude.ai/design only receives the `OUT` tree). Before the first real upload, either (a) have the build step physically copy `.design-sync/.cache/app.css` into `ds-bundle/.cache/app.css` post-build, or (b) inline app.css's resolved content directly into `ds.css` instead of `@import`-ing it. Not yet resolved - flagging for whoever does the §5 upload pass.
5. **`cfg.tokensGlob`** is currently a **no-op**: `lib/css.mjs`'s `copyTokens()` only does anything when `cfg.tokensPkg` is also set (it looks up `join(nodeModules, tokensPkg)/package.json`), and this repo has no separate tokens npm package - it's a single-package Vite app, not a monorepo. `tokensGlob` is left set (`src/styles/globals.css`, `hamclock-themes.css`, `hamclock.css`, `home.css`) as documentation of intent per the task brief, but it ships nothing; token delivery instead happens entirely through `cssEntry` → the compiled `app.css` (which already contains those files' compiled output, since Vite bundled them into `dist/assets/*.css`). No `tokens/` dir appears in `ds-bundle/`. If a real npm-scoped tokens package is ever split out of this repo, wire `tokensPkg` then.

## 2026-09-09 wave learnings (workspace phone/tablet, #699)

- **Set grew 235 → 242.** Added 7 components: 5 phone canvas cards (`workspace/phone/ContactScreen`, `PhoneBandLadder`, `PhoneContactList`, `PhoneStateStrip`, `PhoneSetupMenu`) + 2 tablet heat-map widgets (`workspace/widgets/HeatMapStrip`, `HeatMapPanel`). - **First wave to seed Zustand stores directly, instead of relying on default state or `.d.ts`-derived crash-prevention props.** These components take zero/near-zero props — target/roster/spots/cursor all come from `useDXStore`, `useOperatingStateStore`, `useWorkspaceStore` — so an honest "populated" state needs real store data, not a prop.
