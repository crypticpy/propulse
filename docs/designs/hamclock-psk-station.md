# Callsign-specific PSK Reporter feed — #287

The global collector uses PSK Reporter's `v2raw_1pc` MQTT sample. Its latest 200 rows cannot establish who heard a particular station. `/api/spots/psk-station?callsign=N0TEST` retrieves a separate callsign-specific 24-hour snapshot for the forthcoming OF/BY station controls and WSJT-X heard-by report. The global collector and modeling pipeline are unchanged.

The public [PSK Reporter retrieval documentation](https://pskreporter.info/pskdev.html) supports `callsign` (both sender and receiver), a negative `flowStartSeconds` up to 24 hours, and recommends retrieval no more often than five minutes. One canonical uppercase callsign is the cache key. Age, direction and band controls must filter that same snapshot locally; they must not create separate provider requests. Portable callsigns are exact, including suffixes.

The endpoint requests 1,000 rows, reads at most 2 MiB under a ten-second deadline covering headers and body, strictly parses XML, rejects error/DOCTYPE/malformed envelopes, and retains the newest 1,000 valid matching rows. A bounded read-only provider check showed `rptlimit=1` returning 993 reports, so the application enforces its own limit. It exposes `limited` at the retained ceiling and `discarded` for invalid, unrelated or out-of-window records. **Counts describe loaded reports, never a guaranteed complete history.** Missing SNR/locators remain null. Frequencies preserve integer Hz.

Success, successful empty, stale last success, and unavailable are distinct. `fetchedAt` advances only on success; `checkedAt` records attempts. Success and failure both impose a five-minute cooldown. The snapshot includes `retryAt` so clients can respect the same cadence. Stale rows retain original observation timestamps; consuming views must filter against the current clock even during outages.

There are at most 128 process-local cache entries, a single in-flight request per callsign, six upstream starts per client IP per five minutes, and 30 endpoint reads per minute. Fresh entries are never evicted to make room for a new call. CDN responses use only the remaining cooldown, without extending the age of a cached snapshot. This shares the existing rate limiter's limitation: process memory resets on cold starts and is not shared across regions. CDN caching reduces duplicate traffic but is not a distributed five-minute lock. A shared durable cache would be needed to guarantee that across deployments. No personal email or invented provider contact is sent.

`saxes` 6.0.0 and its existing `xmlchars` dependency are promoted from the lockfile's test dependency tree to production; their locked versions and integrity hashes are unchanged. No shared `node_modules` install was performed. The endpoint is registered in the portable manifest, so local dev and the LAN bridge serve the same handler.

Validation: ten focused tests cover exact direction/frequency/time, suffix distinction, malformed/empty XML, newest-row bounds, concurrent request reuse, cooldown and cache capacity, stale recovery, method/input rejection, oversized bodies, and a stalled response body. UI work and map integration follow in separate slices; this data endpoint does not yet add a visible tile.
