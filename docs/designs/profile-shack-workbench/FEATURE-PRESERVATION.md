# Existing feature preservation register

The approved station design library is the visual foundation. It does not replace existing product capabilities. This register makes preservation of those capabilities an explicit acceptance condition for the remaining refactor, alongside S01–S17 in [the delivery plan](DELIVERY-PLAN.md). A different layout, name or interaction is acceptable when the underlying task, data and integration remain available. Removing a capability requires an explicit owner-approved scope decision linked here and on its delivery issue.

This is a source audit made on 2026-09-05 for W01 against baseline commit `1b61f7ffdc13615e483cfa37896a910e56f78ac8` (before the new contract files). **Every row below is Pending for delivery and integrated verification.** Finding an existing component, writing a contract, or approving a concept image does not demonstrate replacement parity. Sources describe the checked-out implementation; this document does not assert that deployed RLS, media access, every browser workflow, or every old feature has been tested. No private owner records were inspected or copied. Re-audit consumers before cutover because other agents are developing the application concurrently.

For each row, the implementing agent must attach a merged PR and its verification evidence to the named issue, then link that evidence here and change the status to Verified. Record intentional corrections separately: preserving useful behavior does not require preserving a privacy defect, a silent data substitution, or accidental activation. W21 [#195](https://github.com/crypticpy/propulse/issues/195) cannot retire the old paths until every row has evidence or an explicitly approved exception. W22 [#194](https://github.com/crypticpy/propulse/issues/194) still requires real operator validation.
