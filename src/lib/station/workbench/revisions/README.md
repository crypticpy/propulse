# Setup, revision and layout services (W03 / #176)

These pure services prepare validated, detached, recursively frozen records. They do not write storage, activate a station, publish a profile, contact hardware or run electrical analysis. W04 must commit proposals atomically with immutable revision IDs and a compare-and-swap check against `expectedHead`; in-memory preparation is not a concurrency guarantee.

`resolveRevisionInputs(archive, { instanceIds, locationId, evidenceIds? })` captures explicitly selected live equipment, its models and all referenced evidence, including the full model citation bibliography. Optional evidence IDs pin declarations used by settings or cable lengths. Membership includes unwired accessories and retired historical identities. It does not infer membership from route traversal or invent missing data. Use this helper only when explicitly selecting current inputs for an initial revision or an edit; clone and restore copy their historical source snapshots.

`prepareSetup` returns a new setup and initial revision. `prepareRevision` prepares a fresh immutable revision and advances that setup's draft head only when the supplied expected head matches. Full revision content is explicit; there is no mutable second draft graph. A reviewed operating/publication/experiment reference remains attached to its old revision until its own later reviewed transition.

`prepareSetupClone` creates a setup from a named source revision. Its explicit connection/run/route ID maps must be complete, unique and fresh. All references are remapped together, while physical equipment, port and internal-path IDs remain shared. Original pinned specifications, evidence, private metadata and location are copied; inventory is not duplicated or refreshed. Original setup recovery envelopes are copied unchanged as private provenance, including their original source IDs. `prepareRevisionRestore` appends a fresh revision parented to the current draft head, with explicit restore-source provenance. It preserves both the intervening history and source snapshot. Restoring across setups is rejected. Parent/source provenance cannot cycle. Timestamps record caller-supplied instants, not device-independent ordering; revision identity and expected-head checks establish transitions.

`prepareLayout` and `prepareLayoutUpdate` arrange a specific revision in diagram, list or rack view. Positions may omit unplaced items. Optional `itemOrder` includes every selected equipment ID exactly once, including unwired accessories. Groups, viewport and optional label/port/grid/snap preferences are separate from connectivity and global visual-comfort settings. Updates replace presentation content while preserving identity, view and revision. Moving to another revision requires a new layout proposal with its membership checked. No view owns another electrical graph.

`assessRevisionTopology` reports invalid, incomplete, unsupported or structurally candidate documentation. A candidate is not an engine-supported or safe-to-operate result. Valid unsupported branches retain their documentation reasons. Invalid references/duplicates/disconnected topology produce diagnostics and a private lossless `workbench` recovery envelope containing the original JSON; they do not become a partially fabricated graph. Non-JSON input cannot be captured and receives an explicit recovery-unavailable diagnostic. Recovery is owner data, not a public projection.

## Boundaries and verification

The W03 tests exercise stable multi-run/inline identities, explicit band/power/location intent, immutable pinned inputs, stale-head rejection, historical clone/restore, shared inventory, unsupported topology and lossless recovery. Layout tests assemble proposed records into an archive and verify that revisions, operating selection, experiments and publication references are unchanged.

W04 owns durable storage, transactional concurrency and migration/quarantine integration. W06 owns commands/undo; W07/W08 own supported analysis and operating promotion; W10–W13 own the working editors and accessibility. No existing UI or store imports this module yet, and no preservation-register row is considered complete solely from these service tests.
